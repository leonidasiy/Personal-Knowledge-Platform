Milestone 3F decision

Autonomous hosted browser acceptance

The agent needs a repeatable authenticated browser path before presenting another release. The harness must navigate the deployed application, reproduce stale-result transitions, inspect console and network failures, take screenshots, and clean up its own Library mutations without borrowing personal browser data.

Approaches

A. Recommended

Playwright + Access service token

Pin playwright-core, use the installed stable Google Chrome, and authenticate with a service token allowed only for this Access application.

Security
Dedicated revocable credential; no personal Chrome profile or Google session.
Coverage
Real hosted Access, Worker, providers, D1, routes, DOM, console, and network.
Cost
USD 0 incremental on the existing Access Free boundary; current documented limit is 50 service tokens.
Setup
One service token and one exact-token Service Auth policy; two values stored only in an ignored local environment file.

B

Playwright + persistent personal session

Use a dedicated Playwright profile and ask the user to complete the email login once.

Security
No new Access policy, but stores a personal authenticated session locally.
Coverage
Full hosted browser coverage while the session remains valid.
Tradeoff
Manual renewal, identity coupling, and more sensitive local state.

C

Local browser only

Automate a local server with injected test boundaries and no hosted authentication.

Security
No additional credential.
Coverage
Fast DOM and state testing, but cannot prove Access, deployed assets, real providers, or D1 behavior.
Tradeoff
Useful as a development loop, insufficient as the final release gate.

Recommended Design

  • Use Approach A with a 90-day token named resonance-browser-acceptance.
  • Add a Service Auth policy that includes only that exact service token, while retaining the existing personal email Allow policy.
  • Store CF_ACCESS_CLIENT_ID and CF_ACCESS_CLIENT_SECRET in ignored .env.browser-acceptance; never print or persist their values.
  • Pin playwright-core and use the installed Chrome channel, avoiding a separate browser download.
  • Keep fast deterministic state tests local. Run the hosted browser suite only for release candidates and explicit acceptance work.
  • Allow one reversible production Library mutation using a generated acceptance identity; verify it, then deactivate it.
  • Store redacted screenshots, timings, console categories, response statuses, and Worker version under ignored test-results/ and logs/ for 30 days.
  • Keep the current deployment online while fixing because the failure appears to predate Taddy and rollback would remove the provider without addressing the state defect. Stop further production mutations until the fix passes.
