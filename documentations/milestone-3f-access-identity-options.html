Milestone 3F · Security boundary

How should browser automation become the private owner?

Cloudflare Access successfully validates the Service Auth token. Its signed JWT uses common_name for the service-token client ID and does not carry the user's email, while Resonance currently accepts only mapped email identities.

Recommended

A · Exact service-principal mapping

Extend the existing signed-JWT verifier to accept either one mapped email identity or one exact configured service-token common_name. Map only the approved acceptance client ID to personal-owner-v1.

Security
Strong. Signature, issuer, audience, expiry, and exact principal mapping remain mandatory. Browser-supplied identity claims stay rejected.
Operations
Add one Worker secret, ACCESS_ACCEPTANCE_SERVICE_TOKEN_ID, containing the existing non-secret client ID. The client secret remains only in the local acceptance environment.
Automation
Fully unattended and compatible with the current reversible browser journey.
Recurring cost
USD 0.00 under the existing Cloudflare Access Free setup.

B · Persist an interactive user session

Authenticate once through the Google/Access login screen and retain Playwright storage state for later acceptance runs.

Security
Weaker local artifact posture: an identity session cookie must be stored, rotated, protected, and excluded from logs and source control.
Operations
Periodic manual login is required when the session expires.
Automation
Not fully unattended and harder to reproduce in isolated environments.
Recurring cost
USD 0.00, with higher maintenance cost.

C · Acceptance-only application bypass

Add a separate custom credential or bypass route specifically for testing.

Security
Not recommended. It creates a second authorization mechanism and increases the production attack surface.
Operations
Requires separate credential rotation, routing, monitoring, and rollback.
Automation
Unattended, but at an unjustified architectural cost.
Recurring cost
USD 0.00, with the highest engineering risk.

Proposed tests for Option A

  • Identity JWT with one mapped email continues to authenticate.
  • Service JWT with the exact configured common_name authenticates as the approved owner.
  • Unknown service IDs, missing principals, ambiguous email-plus-service claims, invalid signatures, wrong audiences, and expired tokens remain distinct failures.
  • Missing service-token configuration disables only service authentication and preserves interactive user access.
  • The hosted Library API returns success, browser artifacts remain redacted, the temporary source is removed, and completed review history is unchanged.
  • The init-script hook receives a dedicated sanitized browser-setup failure instead of being mislabeled as a Chrome launch failure.
